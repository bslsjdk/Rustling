# Rustling 项目计划

状态：**项目所有者已确认；P0 进行中，后续阶段仍按验收逐期开启。**

本文规定 Rustling 的产品边界、架构和阶段验收。它是 Android 发行线自己的计划，不替代
[Starling 路线图](../roadmap/starling.md)或 [Horizon 路线图](../ROADMAP.md)。日期和未测量的性能数字
不写成承诺；每个阶段以可复现的行为和真机结果验收。

## 1. 北极星

**Rustling 是中文友好的 Android 独立发行版：一个 APK 内提供自己的启动器、实例、模组和
整合包管理，以高性能 Rust 原生模组为主要代码模组形态。**

Horizon 继续提供游戏内核。Rustling 负责 Android 启动、系统交互、实例、中文体验、模组工作流、
稳定性与发布；通用玩法修复优先回流 Horizon。我们不维护一份无谓分叉的完整游戏核心。

这里的“高性能”必须通过相同设备、世界、画质、操作路径下的帧时间、内存、温度和稳定性测量证明，
不能仅由“使用 Rust”推导。无模组时保持原版代码路径与既有 parity 检查。

## 2. 已确认的决策

- 界面：**Kotlin 原生 Android UI**；共享业务：**Rust**。
- 交付：一个 APK，启动器与游戏是不同界面；游戏继续横屏，启动器支持竖屏与横屏。
- 中文：启动器中文优先，跟随系统并可手动切换；同时逐步补齐 Android 游戏内自有界面。
- 模组：同时支持现有 `.hmod` 内容模组与 `.hnmod` Rust 原生模组，不发明第三种运行时。
  原生模组运行快，但安装组合需要重新编译游戏；启动器必须把这个成本讲清楚。
- 整合包：以可复现的实例为单位，记录来源、版本、哈希、启停状态、兼容结果与必要配置。
- Java Mod：复用 `horizon-port-pack` 的扫描、数据/资源迁移和覆盖报告；行为代码需要原生移植，
  **不承诺任意 Forge/Fabric/NeoForge jar 一键完整转换**。
- 原生模组构建：复用现有受控构建服务/GitHub 路径及 APK 内动态库切换，不要求手机本地编译完整游戏。
- 包名与迁移：实现期保留现有 application ID、签名升级链和数据目录，先提供产品显示名与品牌层；
  是否迁移到新 application ID 另立兼容方案，不能与启动器重写混在一起。

## 3. 先复用，不重写

审计已经确认下列能力存在。实现前应写“调用点与缺口”，不得以路线图中的旧 “Later” 标签为依据重做。

| 现有能力 | 复用位置 | Rustling 要补的部分 |
|---|---|---|
| 无窗口模组目录、搜索、校验下载、安装 | `crates/starling-catalog` | Android 启动器状态接口、实例目标、错误中文化 |
| 内容模组与原生模组加载 | `horizon-mods`、`game/mods.rs` | 统一实例清单与可恢复操作，不另造加载器 |
| Android 原生模组导入、编译、下载与切换 | `game/native_builds.rs`、`NativeMods.java`、`docs/starling-native-mods.md` | 启动器进度/取消/重试、版本冲突说明、故障恢复 |
| Java Mod/整合包扫描与移植 | `horizon-port-pack`、`docs/modpacks.md` | 手机可理解的覆盖报告、任务编排和产物管理 |
| 桌面实例、导入导出、模组与整合包逻辑 | `launcher/src/lib.rs` 中的非 UI 模块 | 审计桌面依赖，抽取可共享 crate，而非链接整个 GPUI 启动器 |
| Android 独立进程入口 | `packaging/android/.../LauncherActivity.java` | 扩展现有入口，保留导入、重启和崩溃恢复路径 |
| 账号、下载和后台工作 | `starling-account`、`WorkService` 等 | 与启动器导航、实例状态和任务中心衔接 |
| 中文翻译框架与词表 | `launcher/src/i18n.rs`、`launcher/lang/zh.json`、游戏 `lang` | 建立 Android 资源映射，清理新增和既有硬编码 |
| 性能与崩溃诊断 | `docs/android-diagnostics.md` 所列生产工具 | 固定真机场景、基线与回归报告，不另造一套遥测 |

## 4. 目标架构

```text
Kotlin 启动器（首页 / 实例 / 模组 / 整合包 / 设置）
                    │ 版本化命令与状态 DTO
                    ▼
        共享启动器核心（Rust，无 UI；名称待 P0 审计）
        ├─ 实例与选择       ├─ 模组清单和校验
        ├─ 整合包导入导出   ├─ 任务、取消与恢复
        └─ 移植覆盖报告     └─ 构建状态与诊断摘要
                    │
      ┌─────────────┼──────────────────┐
      ▼             ▼                  ▼
starling-catalog  horizon-port-pack   Android 平台适配
                                      文件/账号/下载/启动
                    │
                    ▼
        现有 Horizon/Starling 游戏入口
```

### 4.1 Kotlin 与 Rust 的边界

- Kotlin 负责导航、系统文件选择器、权限、账号交互、通知、后台任务生命周期和启动 Activity。
- Rust 负责实例格式、依赖与冲突、模组清单、哈希、整合包、移植分析和可测试的状态转换。
- 先审计再确定桥接。DTO 带 schema 版本；错误使用稳定代码加可翻译参数，不让 UI 匹配英文错误句子。
- 文件操作由 Rust 核心接受**已授权的实例根目录**，Android 适配层负责 SAF/content URI 与私有目录；
  不把 content URI 当普通路径传入文件 API。
- 长任务有任务 ID、进度、取消、断点或安全重试策略。进程被杀后不得把半成品当成已安装。
- 不在 UI 线程做哈希、解压、网络或大型清单操作；网络/线程模型在桥接审计时依据现有 Rust 实现确定。
- 禁止一份实例状态分别由 Kotlin、游戏和桌面启动器无协调地改写。写操作采用锁/原子发布和修订号。

### 4.2 实例模型

每个实例至少记录：稳定 ID、显示名、Horizon/Starling 精确修订、资源版本、原生 Hook API、模组文件与
SHA-256、启停状态、来源、必要配置、资源包/光影选择和覆盖报告。

- 实例的模组、配置与资源选择相互隔离；存档默认归属实例，但第一期不提供跨实例自动合并存档。
- 原生模组组合必须绑定构建指纹。当前运行组合、下次启动组合和已编译组合分别显示。
- 内容冲突、缺依赖、命名空间冲突、版本不符和未编译状态在启动前说明；不能只到游戏里才报错。
- 删除实例、移除模组和覆盖配置均需确认与适用的备份。未获确认不得动用户现有世界。

### 4.3 中文与术语

统一使用：**实例、内容模组、原生模组、整合包、资源包、光影包、兼容报告、编译、缺失依赖**。

- Kotlin 使用 Android 字符串资源；Rust 返回消息键/错误码和参数；游戏使用 `Text::tr`/`lang::get`。
- 可复用桌面 `zh.json` 的译文，但不把英文原文当跨模块永久主键；新共享 DTO 使用稳定消息 ID。
- 中文覆盖包含导航、设置、账号、安装、模组、构建、权限、错误、诊断和空状态，不只覆盖首页。
- 缺翻译回退英文；自动检查新增硬编码、占位符不一致、缺失键与基础布局溢出。
- 第三方 Mod 自己提供的文本不由启动器承诺全部翻译；可展示 Mod 自带中文语言文件及覆盖状态。

## 5. Java “转换器”的真实边界

26.3 的资源准备会临时运行 Java 导出器，再删除运行时；这不等于能机械翻译任意 Java Mod。Rustling
将导入分为四级，并在安装前显示结果：

1. **可运行**：所需内容/行为已有等价实现，且对应检查通过。
2. **部分可运行**：方块、物品、配方、战利品、标签、世界生成 JSON、模型、贴图、语言等可迁移；
   机器、菜单、实体 AI、网络、Mixin 或其他行为明确列为缺失。
3. **需要原生移植**：行为需 `.hnmod`、新 Hook 或人工/agent 移植与原版对照验证。
4. **不可导入**：无可迁移内容、版本过旧、格式/许可/依赖不满足，或校验失败。

转换器只生成用户本地的候选内容模组、清单和报告，不把“jar 已解包”称为“Mod 已兼容”。复杂 Mod
的原生移植是持续工程，不是启动器里的一个按钮。许可规则按 `CONTRIBUTING.md` 与 `docs/modpacks.md`
执行；本地处理不自动获得再分发权。

## 6. 分阶段交付

### P0：共享核心与迁移审计（第一道实现任务）

交付：模块依赖图、现有 launcher 非 UI 模块的 Android 可复用性清单、实例格式草案、桥接 DTO/错误模型、
迁移与回滚策略、真实 APK 构建/真机测试基线。

验收：
- 明确每项复用、抽取或保留 Android 专用，没有“重写后才知道冲突”的黑盒。
- 旧启动、文件导入、重启恢复、存档与已编译原生模组路径保持可用。
- 主机单元测试与 Android 最小桥接冒烟测试可重复执行。

### P1：中文启动器 + 真实实例 + 模组闭环

页面：首页、实例、模组、整合包、设置。整合包页在本期只展示真实状态与阶段说明；导入、导出和
在线搜索等到对应能力完成时再开放，不放无功能按钮。

验收：
- 首次启动进入中文启动器；可切换英文；旋转、返回、后台恢复不丢任务状态。
- 创建/选择真实实例，展示实际版本、模组与错误；启动正确的游戏实例。
- 导入 `.hmod/.hnmod`，启停、移除、刷新状态；原生模组进入现有编译流程并显示三态组合。
- 新启动器可见文案无未翻译硬编码；错误、权限、诊断与构建状态也有中文。
- 在至少一台真实 ARM64 手机完成安装→配置→启动→返回启动器→再启动，保留实际设备与结果。

### P2：可恢复整合包

验收：
- 实例可导出为带版本化 manifest 的整合包；导入后还原精确修订、模组版本/哈希、启停与配置。
- 外部文件先列来源和许可，按来源校验获取；不能合法再分发的内容不直接打入公开包。
- 缺文件、缺依赖、哈希不符、磁盘不足和中途取消均不产生“可启动”的坏实例。
- 同一实例导出→全新导入→启动的行为一致；保留覆盖报告与导入日志。
- 默认不导出账号、令牌、诊断隐私或整个存档；世界的显式备份/分享另设确认。

### P3：Java 移植入口与生态工作流

验收：
- 从启动器选择 jar、`.mrpack` 或本地 CurseForge 整合包，得到逐项兼容报告和依赖顺序。
- 数据/资源可迁移项复用 `horizon-port-pack`；部分移植项默认不伪装完整启用。
- 原生候选产物进入现有构建服务；失败能定位到 Mod/Hook/版本，不会破坏原实例。
- 对一个许可允许的最小内容 Mod 和一个含行为 Mod 做端到端样例：前者可玩，后者明确展示缺口；
  不用自制“永远能转”的玩具样例冒充任意 Java Mod 兼容。

### P4：性能、稳定性与发布门槛

先记录基线，再由项目所有者确认目标设备与数值门槛。每次比较使用相同资源、世界、路径、画质和模组。

至少报告：冷/温启动、资源准备、世界加载、帧时间 p50/p95/p99、慢帧、内存峰值、热状态、构建成功率、
崩溃/ANR、后台恢复和存档完整性。缺传感器或不支持 GPU 时间戳要标“不可用”，不能填零。

发布前还需通过：真实账号与离线边界、慢网/断网、存储不足、系统杀进程、APK 升级、旧原生构建失效回退、
中文布局、公开树检查和适用 parity/Mod 端到端测试。

## 7. 明确排除

- 不承诺通用 JVM 在 Android 游戏内运行 Java Mod。
- 不承诺任意 Java 字节码/Mixin 自动转 Rust，或复杂整合包短期 100% 移植。
- 不把 GPUI 桌面窗口原样搬上手机，不维护两套独立模组业务逻辑。
- 不在无真机数据时宣称性能提升、兼容率、汉化完成或“电影级”体验。
- 不将 Mojang 文件、准备好的资源、Mod jar 或无再分发权的移植资产提交到公开仓库。
- 不在第一阶段重做游戏核心、在线账号体系、构建服务或另一套模组 API。
- 不以一个超大 PR 同时完成品牌迁移、启动器、实例、移植器和游戏修复；每期继续拆小 PR。

## 8. 实施纪律与风险

- 当前工作分支为 `starling`；开始前再次检查上游、未提交修改、相关 issue/PR 和有效 claim。
- 新计划文档确认后，只为 P0 建第一张实施清单；未验收 P0 不同时展开 P1/P2/P3。
- 功能 PR 保持小且可回退，附 `tools/pr_ready.py`、触及 crate 测试、适用 parity 和真机证据。
- 任何用户可见字符串从加入时即可翻译；行为变化必须有独立预期值或 vanilla oracle。
- 最大风险依次为：桌面逻辑隐式依赖 GPUI/主机路径、双写实例状态、原生模组版本漂移、后台进程死亡、
  Java 移植被误解为全兼容、品牌/包名迁移破坏升级。对应措施是先审计、单一写入者、构建指纹、
  原子发布、明确报告和独立迁移阶段。

## 9. 第一项等待确认的实施范围

仅 **P0：共享核心与迁移审计 + 最小 Android 桥接冒烟**。它不应趁机完成整个 UI 或 Java 转换器。
P0 结果经双方查看后，再确定 P1 的第一张页面和第一个端到端切片。
